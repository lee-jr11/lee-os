# P1.1 — Artifact / File Service

P1.1 gives LeeOS a file-type-neutral path to own bytes after a producer finishes. Artifact metadata is not treated as proof of ownership: a managed artifact is committed together with its bytes, digest, size and registration event, and the service verifies the bytes again on retrieval.

## What it provides

- PostgreSQL `bytea` storage, independent of a worker runner's temporary filesystem.
- Project-scoped artifact records, optional run association and immutable metadata/content.
- SHA-256 and byte-count verification before returning content.
- Idempotent registration, keyset-paginated listing, metadata lookup and attachment download.
- Worker-origin registration only while the exact execution envelope, worker ID, fencing token, lease, grant and run remain valid.
- A single transaction for metadata, bytes and the `artifact.registered` event. A database constraint also prevents managed metadata from committing without matching bytes.
- Legacy external-reference records remain metadata-only; the service does not pretend their referenced content is retrievable.

There is no file-type-specific generation or validation in this service. The service validates safe filename syntax and MIME type syntax, but it does not inspect file signatures, render previews, send files or delete artifacts. P1.2 now supplies a separate DOCX generator and validator above this file-type-neutral storage layer.

## Bounded storage and opt-in

The managed database byte ceiling is 10 MiB per artifact, 100 MiB per project and 500 MiB total. Quota checks serialize in PostgreSQL so concurrent processes cannot overrun the shared limits. The database provider may still charge for database size, backups or network use; LeeOS does not independently verify those commercial limits.

Apply migration 013 (and 014 when using P1.2) to the intended database, confirm that database's included storage allowance and overage settings, then set `LEEOS_ARTIFACT_STORAGE_ENABLED=1` in the private server environment. It is disabled when unset or set to any other value. Keep `.env` and deployment secrets out of Git. Enabling this option does not provision a storage service or change the database plan.

## Worker and remote-runner boundary

A worker should pass generated bytes directly to `createArtifactStorage(...).register(...)` with `creator: 'envelope-worker'` and the `workerClaim` returned by the durable worker store. Registration checks the active database lease and fencing token at the write transaction. A stale worker is rejected, so it cannot register output after ownership transfers. The worker must finish this registration before its GitHub Actions runner exits; no runner-local path is considered durable storage.

P1.1 supplies the callable core service and database representation. P1.2 now invokes it from the same durable worker after independent validation. Local fixture verification proves the integrated path; remote artifact upload and P0.5 live deployment remain pending.

## Owner API

All routes use the existing owner API authentication and loopback-only boundary.

```text
POST /api/v1/projects/{projectId}/artifacts
GET  /api/v1/projects/{projectId}/artifacts?limit=25&after={artifactId}
GET  /api/v1/artifacts/{artifactId}
GET  /api/v1/artifacts/{artifactId}/content
```

For registration, send raw bytes as the request body with `Content-Type` set to the media type, `X-LeeOS-Artifact-Name` set to a URI-encoded filename, `Idempotency-Key` set to a stable request key, and optional `X-LeeOS-Run-Id` set to the owning run. The API caps the streamed request before buffering it. Repeating the same key and content returns the original receipt; reusing that key for different content returns a conflict.

The content route returns an attachment with `nosniff`, a restrictive content security policy, a SHA-256 ETag and `Cache-Control: no-store`. Metadata responses do not expose the internal storage URI.

## Verification and operating limits

`tests/artifact-storage.test.ts` covers disabled-by-default behavior, worker fence rejection, persistence through a database close/reopen, byte-for-byte retrieval and digest metadata, idempotency, keyset pagination, invalid metadata, project/run scope, quota enforcement, database immutability, the metadata-plus-bytes commit rule and request-size limits.

Artifacts are append-only in P1.1. There is no delete, retention, restore, backup-management or missing-file repair control yet. Use the database's own backup/restore process and account for artifact bytes in its storage budget. The Hub has no artifact browser yet; the owner API supports retrieval. These controls and presentation belong to later lifecycle/Hub work.
